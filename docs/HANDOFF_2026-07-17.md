## 0. GPU 安全警告（最高优先级）

本机刚经历过一次 GPU/驱动异常，并已通过整机重启恢复。后续操作必须保守：

1. **禁止未经用户明确确认执行以下操作：**
   - `nvidia-smi --gpu-reset`
   - PCI remove/rescan、FLR、驱动卸载/重载
   - 停止显示服务、GNOME、向日葵、Tailscale 或 SSH 相关服务
   - EGL/GPU 渲染探测，尤其是曾导致进程进入内核 `D` 状态的测试
   - `kill -9` 不明进程或任何可能属于用户的 GPU 进程
2. 做 GPU 操作前，必须先说明：要运行的完整命令、使用哪张卡、显存预期、持续时间、风险、停止方式，并等待用户确认。
3. 优先做静态检查、`--dry-run`、CPU/OSMesa 小规模验证；不要直接启动全量评估或训练。
4. 任何试跑都必须设置明确边界：GPU 编号、任务数量、episode 数、超时、日志路径。不得让脚本因任务集展开而意外运行上万任务。
5. 不得默认占用所有 GPU。训练是否多卡并行，需要先根据实测显存与代码的并行机制设计，再征得用户确认。
6. 不要把 `nvidia-smi` “No running processes found” 当成绝对依据；驱动异常时它可能无法列出卡上的实际持有者。
7. 如再次出现 `Unknown Error`、`ERR!`、命令卡住或进程进入 `D` 状态：立即停止新增操作，保留日志并向用户汇报，不继续尝试 reset/FLR。

## 1. 实验最终目标

项目主线是 **OpenVLA-OFT + RIPT-VLA LOOP + Robustness-Aware Reward（RA-LOOP）**。

主要研究问题：能否不增加额外 SFT 合成数据，仅在 RL/post-training 阶段引入鲁棒性训练信号，改善 VLA 在扰动环境下的泛化。

奖励设计草案：

```text
R_total = R_success + lambda_c * R_consistency + lambda_r * R_recovery
```

- `R_success`：任务成功奖励
- `R_consistency`：同一任务不同扰动下的动作一致性
- `R_recovery`：从扰动初始状态恢复并完成任务的奖励

### 基准定位

- **LIBERO-Plus 是主要鲁棒性评估集。**
- 原版 LIBERO 不是主结果，只作为非退化对照，检查鲁棒性训练是否损害标准任务性能。
- 原型阶段的关键 gate：
  - Plus Robot-init 相对 OpenVLA-OFT baseline 至少提升 **3 个百分点**；
  - 原版 LIBERO 性能下降不超过 **2 个百分点**。
- 训练语义仍会使用原版 LIBERO 任务/轨迹，并在 rollout 中注入 Plus 扰动；这不代表实验目标变回原版 LIBERO。

OpenVLA-OFT / LIBERO 评估的正确 Conda 环境不是系统 Python，而是：


启动评估时还必须设置：

```bash
export PYTHONNOUSERSITE=1
```

原因：如果使用裸 `python3`，tmux 会解析到 `/usr/bin/python3`，其中没有
`draccus`。即便使用正确 Conda Python，如果不设置 `PYTHONNOUSERSITE=1`，
`~/.local/lib/python3.10/site-packages` 中的旧版 `transformers` 仍可能优先于
Conda 包加载，并因缺少 `AutoImageProcessor` 导入失败。

已在系统终端使用以下安全边界验证正确环境：

- `PYTHONNOUSERSITE=1`
- `CUDA_VISIBLE_DEVICES=""`（验证期间对进程隐藏全部 GPU）
- `MUJOCO_GL=osmesa`
- `PYOPENGL_PLATFORM=osmesa`

以下导入全部通过：`draccus`、PyTorch、`AutoImageProcessor`、OpenVLA 的
`run_libero_eval`、LIBERO benchmark。验证中 `torch.cuda.is_available()` 为
`False` 是刻意隐藏 GPU 的预期结果；TensorFlow 的 `CUDA_ERROR_NO_DEVICE` 也属
同一原因，不是驱动故障。受限终端曾出现 Numba cache locator 错误，这是沙箱
不能写 Conda `site-packages` 所致；系统终端验证可通过。
